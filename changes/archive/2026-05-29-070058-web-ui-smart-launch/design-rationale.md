# Design Rationale: web-ui-smart-launch

## Context

`mspec new` の目的はチェンジ作業を即座に開始できる状態にすることだが、Web UI を別途手動で起動する必要があり、操作が中断されていた。既存の `launchWebUiIfNeeded` 関数は `new.ts` から呼ばれていたが、判定ロジックが `isAlive(pid)` シグナル確認のみで不十分だった。

複数プロジェクトを並行して作業する環境ではデフォルトポートの衝突が日常的に発生し、起動エラーが出て手動でポートを変更する必要があった。また `isAlive(pid)` はゾンビプロセスや PID の再利用によって誤判定することがあり、すでに起動していない Web UI を「起動済み」と認識して URL を表示してしまうケースがあった。

セキュリティ面では、候補ポートを先取りした悪意あるプロセスが `/__mspec/health` を偽装して mspec の書き込み API（PATCH /api/...）への誘導を試みるリスクがある。ローカルツールではあるが、ファイル書き込みを伴う API を持つサーバーを自動起動するため、誤再利用防止のトークン照合は必須の防衛策として設計に組み込んだ。

## Decisions

### トークン生成をランチャー側で行う理由

サーバー起動後に PID ファイルからトークンを読み戻す代替案では、`waitForPid` のような書き込み完了ポーリングが必要になる。ランチャー側で `crypto.randomUUID()` を生成して spawn 引数として渡すことで、HTTP 応答が返ったタイミングで即座にトークン照合が完了し、待機ループが不要になる。

### `waitForPid` を HTTP ポーリングに完全置換する理由

PID ファイル書き込みが完了しても Fastify がまだポートをリッスンしていないタイミングが存在する。HTTP ヘルスチェックの 200 応答を起動完了の定義にすることで、「ファイルは書けたがサーバーはまだ動いていない」状態を排除できる。追加の起動確認ステップも不要になるため、全体としてシンプルになる。

### PID ファイル形式を JSON に変更する理由

現行の `pid:port` プレーンテキスト形式はフィールド追加に対して脆弱である。FR-011 では `projectRoot` と `token` の 2 フィールドが追加され、将来的にさらに拡張される可能性もある。JSON への移行は `readPid`/`writePid` の変更コストが低く、後方互換をあえて保つ必要もない（旧ファイルはパース失敗で自動再起動するため）。

### `net.createServer` を外部ライブラリなしで使う理由

`detect-port` や `portfinder` は内部的に `net.createServer` と同等の処理をするラッパーである。既存コードの `isPortFree` が同じアプローチで実装済みであり、`127.0.0.1` バインドの明示化という修正だけで再利用できる。外部依存を追加しないことはセキュリティ審査・バンドルサイズ・メンテナンスコストすべてにおいて有利である。

## Alternatives Considered

- **`portfinder` npm**: 連続スキャンで空きポートを自動発見する。予測可能な固定リストより柔軟だが、3847 など「覚えやすいデフォルト」への引力がなくなる。ユーザーが URL を手入力する場面で不便。
- **サーバー生成トークンの PID ファイル書き戻し**: サーバー起動後に PID ファイルを更新する。`waitForPid` のポーリングが残り続けるため、HTTP ポーリングとの二重待機が生じる。
- **HTTP 認証トークン（書き込み API 保護）**: SEC-002 でローカルトークンを全書き込み API に必須化する選択肢も検討した。`mspec open` の主要ユーザーはローカル開発者のみであり、`127.0.0.1` 強制バインドで外部露出を防ぐ本設計で十分とした。

## Trade-offs

- `.mspec/ui.pid` の形式が破壊的変更になる。既存ファイルは次回起動時に自動で上書きされるため影響は軽微だが、テストで旧形式を参照しているコードはアップデートが必要。
- HTTP ポーリングのタイムアウト（5 秒）はサーバー起動が遅い環境でタイムアウトが発生する可能性がある。Fastify の起動は通常 100ms 以内のため、実運用では問題ないと判断した。

## Rejected Options

- **`0.0.0.0` バインドのオプション化**: ローカルツールの要件からリモートアクセスは Non-Goal とした。設定で切り替えられるよりも、常に `127.0.0.1` のほうがデフォルトセキュアの原則に合致する。
- **PID ファイル名を `web-ui.pid` に変更**: 記述的な名前だが、既存コードの `ui.pid` を参照している箇所のリネームコストが発生する。proposal 後の research で現行維持が確定済み。
